## B. Техническое устройство

### B.1 Архитектура

Плагин **не заменяет** навигацию Unreal, а подменяет *реализацию поиска пути* в навмеш-объекте:

- `AAPS_NavigationData : ARecastNavMesh` — собственный класс навмеша. Он наследует Recast и переопределяет статический делегат `FindPath`, который вызывает движок. Переключение режима — одно поле `PathAlgorithm` в `APS_NavigationData` (per-world, в отличие от `AIMoveTo`).
- Навигационная поверхность — **штатный Recast/Detour** Unreal (собственного навмеша нет). «No engine source modifications are required».
- Движение агента остаётся штатным (`AIMoveTo`/`BT MoveTo`/XAI MoveTo). Плагин добавляет **интерфейс** `UAPS_MoveToInterface`, через который агент возвращает параметры маршрута.

### B.2 Режимы поиска (`EAPSPathAlgorithm`) — в установленной версии **пять**

| Режим | Что делает |
|---|---|
| `EngineOnly` | Штатный Recast-поиск движка, APS не участвует |
| `APS_Arc` | Штатный поиск Recast + **постобработка геометрии** пути (дуги) |
| `APS_LowLevelTiles` | Собственный поиск по **тайлам** навмеша (`APS_DetourNode`, с LOS-ускорением) |
| `APS_LowLevelArc` | Тайловый поиск + дуги + Lane Offset (основной режим, 127 KB кода) |
| `APS_Experimental` | Дополнительный экспериментальный режим (в описании Fab **не упоминается** — подтверждено только по коду) |

Переключение — в `APS_NavigationData`; параметры per-agent — через `IAPS_MoveToInterface::GetMoveToParameters(ArcStrength, NumMidPoints, MidpointMode, LaneOffset)`.

### B.3 Построение криволинейного маршрута (`APS_PathMode_APSArc.cpp`)

**Принципиальный вывод: плагин сначала получает обычный путь и затем меняет его геометрию — он не ищет альтернативный обход препятствия «с нуля».** В коде это видно по структуре: поиск пути выполняется штатными средствами, а ниже идёт переписывание полилинии.

Алгоритм дуги (по подтверждённому коду):

1. Берётся исходная полилиния; выбирается **самое длинное ребро** (2D).
2. Для этого ребра перебираются **9 кандидатов** на промежуточную точку: 3 позиции вдоль прямой (t = 0.40 / 0.50 / 0.60) × 3 боковых отклонения (s = 1.00 / 0.70 / 0.45) × выбранная сторона.
3. Каждый кандидат **проецируется на навмеш** (поиск ближайшего полигона) с откатами на 0.6× и 0.3× амплитуды; если проекция не удалась — кандидат отбрасывается.
4. Кандидат разбивается на **две половины, каждая из которых — реальный результат поиска пути** (не интерполяция!). Это гарантирует, что сегменты остаются на проходимой поверхности.
5. Отбраковка: «разворот» в шарнире (dot < −0.8).
6. Оценка кандидата: `2.0·зазор − 1.0·штраф_угла − 3.0·штраф_обратного_движения − 5.0·штраф_неверной_стороны`; побеждает максимум.
7. **Ограничение растяжения**: если новая длина ребра превышает исходную более чем на 60 % (первый шаг) или 25 % (последующие) — сегмент отклоняется.
8. Многоточечный режим (`NumMidPoints > 1`): шаг повторяется; сила дуги на каждом следующем шаге затухает как `0.4^step`; вставляется обратно в полилинию; на концах удаляются точки ближе 5 units к соседям.
9. Одноточечный режим (`NumMidPoints == 1`) — частный случай того же механизма.

Параметры (`FAPSArcPathRequest`): `MinArcDistance` (по умолчанию **300** — ниже этого расстояния дуга выключается), `ArcStrength` (**> 0 — изгиб вправо, < 0 — влево**), `NumMidPoints` (число опорных точек, **не** итоговое число точек пути — это прямо оговорено и на Fab).

`MidpointMode`: `SmoothCurve` и `Wavy` (в Fab — «Wavy / Humps»); реализация выбора режима — в `APS_PathMode_LowLevelArc.cpp` (ветвление по `EAPSArcMidpointMode`).

Асинхронность: `APS_AsyncArcPathTask` — построение дуги выносится в задачу (`DoWork`), результат возвращается в игровой поток.

### B.4 Lane Offset (разнесение маршрутов)

- Смысл: **боковое смещение маршрута вокруг поворотов и манёвров**, величина — `LaneOffset` (в Unreal units), знак выбирает сторону; 0 — отключено.
- В `APS_PathMode_LowLevelArc.cpp` (47 упоминаний) реализовано как:
  - **угловое смещение**: `CornerLaneOffset = CornerOffsetDir · (LaneOffset · CornerStrength)` — на повороте путь сдвигается в сторону;
  - **«maneuver zones»**: окна lookahead (`|LaneOffset|·1.25`, в пределах 100–400) и минимальный интервал между углами (`|LaneOffset|·0.9`, 80–260);
  - **инъекция бокового маршрута**: при `|LaneOffset| ≥ 180` (`GManeuverSideRouteMinLaneOffset`) плагин может **подставить альтернативную ветку** в сторону, а не только сместить путь;
  - **адаптивное сглаживание углов** (`BuildAdaptiveCornerFilletPath`).
- Доступность смещённой траектории контролируется: точки проецируются на навмеш, а «неверная сторона» штрафуется оценкой.
- Разные значения для разных агентов возможны: параметры приходят из `IAPS_MoveToInterface` **каждого** актора, поэтому у каждого агента своя величина и знак.
- **Разница между «визуальным разнесением» и «динамическим избеганием столкновений»**: Lane Offset — это геометрия маршрута; избегание столкновений между агентами остаётся на Detour Crowd (`APS_CrowdFollowingComponent`, `APS_AIController`, опционально `bBuildCrowdCompatiblePathCorridor` / `bRebuildCrowdCorridorAfterArc`).

### B.5 Перестроение маршрута и поведенческие профили

- «Следующий запрос пути использует текущие настройки» — параметры читаются на каждый запрос ⇒ смена профиля (патруль/погоня) применяется к **следующему** `MoveTo` ✓.
- В коде есть: `APS_AIController` (обёртка для Detour Crowd), `APS_CrowdFollowingComponent` (следование по кривым точкам), интерфейс `FindCustomPath(Start, End, OutPath, ArcStrength, World, bUseCustomPath, bFound)`.
- **Важно по лицензионно-техническому смыслу**: документация и страница Fab прямо говорят — *«Find Custom Path accepts your own world-space route. **Your code handles its validation**»*. То есть **валидацию пользовательского маршрута APS не делает** — это зона ответственности игрового кода.

## D. Применимость к WWG

### D.1 Уровень 1 — корректность навигационной поверхности (это и есть настоящая проблема)

**Что реально используется в Unity-проекте сейчас** (по коду, не по документации):

| Элемент | Факт |
|---|---|
| Поиск пути | `ArenaTacticalMap.cs` (40 KB): A* по комнатам (`FindRoomRoute`) + A* по сетке внутри комнаты (`TryFindPathInsideRoom`), сетка `cellSize = 1.5 m` |
| Проверка проходимости | `IsWorldPositionWalkable`: отступ от границ комнаты + `Physics.OverlapSphere` (радиус **0.55**, центр на высоте **+0.8**), любой коллайдер (кроме врагов и игрока) делает клетку непроходимой; коллайдеры `CoverPoint` — прямо запрещены |
| Агент | `agentRadius = 0.65`, `obstacleCheckRadius = 0.55` |
| Цель врага | `EnemyController`: при укрытии — `MoveTowardsKnownTarget(currentCover.transform.position, moveSpeed)`; при провале A* — прямой ход `MoveDirectlyToTarget(target, speed)` |
| Вертикаль | `MoveDirectlyToTarget` и `MoveInDirection` **обнуляют Y** ⇒ вертикальное движение не задаётся ИИ; сетка 2D; точки укрытий стоят **рядом** с объектами (ящик z = ±0.9, укрытие ±1.15, забор ±1.2) на высоте 0.08–0.38 м |

**Подтверждённые по коду дефекты, объясняющие «враги забегают на укрытия и подпрыгивают»:**

1. **Клетка сетки грубее радиуса агента.** Шаг 1.5 м и `agentRadius = 0.65` против проверки `obstacleCheckRadius = 0.55` ⇒ путь может идти в ~0.65 м от поверхности ящика, тогда как капсула врага имеет радиус 0.5 ⇒ физический зазор ≈ 0.15 м. Враг идёт вплотную и **физика поднимает его капсулу на ящик** (решение солвера выбирает кратчайшее направление разделения — вверх). Это и есть «подпрыгивание/залезание», а не намерение ИИ (ИИ по Y ничего не задаёт — проверено в коде).
2. **Прямой откат при недостижимой цели.** Когда A* не даёт путь (клетка цели заблокирована, цель внутри объёма препятствия), код идёт напрямую `MoveDirectlyToTarget` — то есть **в препятствие**. Для укрытий это вероятно: клетка, содержащая укрытие/ящик, непроходима, а путь может «не найтись».
3. **Нет разделения «путь до точки укрытия» и «путь по поверхности укрытия»**: укрытие используется как *позиция у стены*, а не как площадка, но цель берётся из той же точки 3D-координат.

**Ответ на исходный вопрос: поможет ли APS?** — **Нет, не напрямую.** APS — это обработчик формы маршрута поверх Recast-навмеша. Он не решает: грубость сетки vs радиус агента, физическое выталкивание капсулы, прямой откат в препятствие. Ни один из механизмов APS (дуга, Lane Offset, боковой маршрут) не устраняет подъём капсулы на препятствие; APS даже не решает, что «препятствие» — это не NavMesh, а физический коллайдер.

### D.2 Уровень 2 — форма маршрута (что APS действительно улучшает)

| Эффект | Может ли APS | Комментарий |
|---|---|---|
| Разнообразие траекторий к одной цели | **Да** | `ArcStrength` + `NumMidPoints` + `MidpointMode` дают разные формы; в WWG это возможно без APS (см. §E) |
| Уменьшение движения «одной колонной» | **Частично** | Lane Offset разносит траектории по ширине; но без Detour Crowd в Unity агенты всё равно сливаются — нужен собственный steering/separation (в WWG уже есть `ApplyEnemySeparation` ✓) |
| Плавные проходы вместо «ломаных» A* | **Да, идея переносима** | в WWG путь строится по сетке 1.5 м ⇒ ступенчатый; сглаживание/филлет — полезно |
| Обходная сторона в ограниченной ситуации | **Да** (идея) | у APS — инъекция бокового маршрута при большом LaneOffset; в Unity то же можно сделать на своей сетке |
| Изменение характера движения по состояниям ИИ (патруль/погоня) | **Да** | параметры per-agent, читаются на каждый запрос |
| **Обход непроходимого укрытия** | **Нет** | это задача проходимости и зазора, а не формы пути |
| **Прекращение «залезания» на ящики** | **Нет** | это физика капсулы + грубость сетки + прямой откат |

**Принципиальное требование соблюдено в анализе:** криволинейная траектория не считается решением обхода препятствий, пока не доказано, что каждый сегмент остаётся на допустимой поверхности и имеет зазор. У APS это обеспечено тем, что половины дуги — **реальные под-пути**, а для Lane Offset — проекцией на навмеш и штрафами за неверную сторону. В WWG аналогичная гарантия возможна только при переходе от «сетка + физика» к «сетка с честным зазором (агентский радиус) + проверка отрезка на проходимость».

### D.3 Что уже есть в WWG и что предлагается реализовать самостоятельно

|---|---|---|---|---|

### E.4 Производительность и совместимость

- Сглаживание через дополнительные запросы пути — основной риск: каждый запрос стоит A* по сетке. Нужны: кэш сетки, ограничение числа запросов, отключение сглаживания для дальних дистанций.
- Проверка отрезка свёрткой — O(длина/шаг) на каждый сегмент; требует кэша проходимости клеток.
- Detour Crowd в Unity отсутствует ⇒ «разнесение колонны» придётся делать собственным steering (база `ApplyEnemySeparation` уже есть).
- Мобильная платформа: бюджет кадра на 200+ врагов — ограничить пересчёт пути (только при смене цели/таймер, не каждый кадр).
